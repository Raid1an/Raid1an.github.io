## 前言：为什么想做一个旅行规划师

起因很简单——我手写了一份日本7天旅游攻略PDF，精确到每段交通的分钟和日元、末班时间锚点、行李寄存全流程、多城市串联、分头行动方案。写完之后我想：这种信息密集、多环节协作的规划任务，不正是 AI Agent 最擅长的事吗？

于是我开始了一个实验：**从零搭建一套多智能体协作的旅行规划系统**。不是用 Dify、Coze 这类平台拖拽，而是自己写每一行代码——理解 ReAct 循环怎么转、工具怎么注册、多 Agent 怎么协作、对话式交互怎么实现。

这篇文章记录了整个过程：从 600 行通用 Agent 框架，到 5 个 Agent 流水线协作的旅行规划师，再到对话式修改攻略——以及踩过的每一个坑。

## 一、先造轮子：600行通用 Agent 框架

### 1.1 ReAct 循环：Agent 的心脏

ReAct = Reasoning + Acting。核心循环只有四步：

```
Thought（思考）→ Action（行动）→ Observation（观察）→ 回到 Thought → ... → Final Answer
```

LLM 负责"思考"和"决定调什么工具"，代码负责"执行工具"并把结果喂回给 LLM。LLM 本身不执行任何操作，它只是"说"要做什么。

我的 `agent.py` 核心循环只有 60 行：

```python
def run(self, user_input: str) -> AgentResult:
    messages = [
        {"role": "system", "content": self.system_prompt},
        {"role": "user", "content": user_input},
    ]
    tools_schema = self.registry.get_schema(self.tools)
    steps = []

    for step_num in range(1, self.max_steps + 1):
        response = self.llm.chat(messages, tools=tools_schema)

        # 没有工具调用 = LLM 认为可以直接回答了
        if not response.has_tool_calls:
            return AgentResult(answer=response.content, steps=steps)

        # 有工具调用 → 执行 → 结果加入对话历史 → 继续循环
        for tc in response.tool_calls:
            messages.append({"role": "assistant", "tool_calls": [tc]})
            observation = self.registry.execute(tc["name"], tc["arguments"])
            messages.append({"role": "tool", "content": observation})
            steps.append(AgentStep(...))
```

就这么简单。LLM 说要调 `search`，代码就调 `search`，把结果塞回对话历史，LLM 拿到结果继续想下一步。直到它觉得"够了"，直接输出文本回答，循环结束。

### 1.2 三层架构

整个框架 15 个文件，约 600 行代码，分三层：

| 层 | 文件 | 职责 |
|---|---|---|
| LLM 接口层 | `llm.py` | 封装 OpenAI 兼容协议，一套代码适配 DeepSeek / Qwen / OpenAI |
| 工具注册层 | `tool_registry.py` + `builtin_tools.py` | `@tool` 装饰器注册函数，自动生成 JSON Schema 给 LLM |
| Agent 核心层 | `agent.py` + `profile.py` | ReAct 循环 + YAML 角色定义 |

**`@tool` 装饰器**是我最满意的设计——写一个普通 Python 函数，加一行 `@tool`，它就自动变成一个 LLM 可调用的工具：

```python
@tool
def calculate(expression: str) -> str:
    """计算数学表达式并返回结果"""
    try:
        result = eval(expression)
        return f"结果：{result}"
    except:
        return "计算失败"
```

装饰器自动从函数签名和 docstring 生成 JSON Schema，LLM 就知道这个工具叫什么、接受什么参数。零样板代码。

### 1.3 Profile 系统：YAML 定义 Agent 角色

每个 Agent 角色用一个 YAML 文件定义——身份、行为指令、工具权限、最大步数：

```yaml
name: route_planner
identity: "旅行路线规划师，擅长安排每日精确到分钟的景点行程"
instructions:
  - "先用 search_xhs_travel 搜索小红书上的真实旅行笔记"
  - "用 map_get_route 计算景点之间的交通时间"
  - "每天最后一段交通必须标注最晚出发时间和末班车时间"
allowed_tools:
  - search_xhs_travel
  - map_get_route
  - calc_latest_departure
  - format_schedule
mode: execute
max_steps: 40
```

这个设计参考了 NeuroBook（一个 GitHub 上 500+ 星的 Agent 项目）的 `allowedToolKeys` 机制——不同的 Agent 有不同的工具权限，路线规划师能调地图工具但不能调预算计算，预算管理能用 `calculate` 但不能搜网页。

## 二、旅行规划师：5个Agent流水线协作

### 2.1 流水线设计

通用 Agent 框架搭好后，旅行规划师是它的第一个应用。核心思路是**流水线调度**——固定顺序，每步输出是下步输入：

```
单城市：路线规划师 → 美食侦察 → 预算管理 → 天气顾问 → 汇总攻略
多城市：城市协调员 → 路线规划师 → 美食侦察 → 预算管理 → 天气顾问 → 汇总攻略
```

为什么用流水线而不是让一个 Leader Agent 自由调度？因为**流程可控**。Leader 模式下 LLM 可能乱跑——调了美食但忘了路线，或者反复调一个工具。流水线保证每步必走、顺序固定。

TravelPlanner 类的核心方法 `plan_single()` 就是按顺序调 4 个 Agent：

```python
def plan_single(self, destination, days, budget, ...):
    # Step 1: 路线规划
    route_result = self._run_agent("route_planner", route_task)

    # Step 2: 美食侦察（输入=路线规划的结果）
    food_result = self._run_agent("food_scout",
        f"以下是路线规划师安排的行程：\n{route_result}\n...")

    # Step 3: 预算管理（输入=路线+美食）
    budget_result = self._run_agent("budget_manager",
        f"路线：{route_result}\n美食：{food_result}\n...")

    # Step 4: 天气顾问（输入=最终行程）
    weather_result = self._run_agent("weather_advisor", ...)

    # 汇总
    guide = self._generate_guide(route, food, budget, weather)
```

每一步的 task 描述里都会嵌入前一步的完整输出，Agent 之间真正"看到"彼此的工作成果。

### 2.2 32个工具：从搜索到地图到天气

整个系统注册了 32 个工具，覆盖旅行规划的每个环节：

| 工具类别 | 数量 | 代表工具 |
|---------|------|---------|
| 内置工具 | 5 | `read_file`, `write_file`, `search`, `calculate` |
| 地图工具 | 3 | `map_search_places`, `map_get_route`, `map_get_distance` |
| 小红书爬虫 | 3 | `search_xhs_notes`, `get_xhs_note_detail`, `search_xhs_travel` |
| 增强搜索 | 3 | `web_search`（Bing/百度/DDG多引擎） |
| 时间约束 | 5 | `calc_latest_departure`（末班车倒推）, `check_time_conflict` |
| 城际交通 | 4 | `city_transport_search`, `calc_intercity_schedule` |
| 行李管理 | 3 | `find_luggage_storage`, `plan_luggage_flow` |
| 天气查询 | 3 | `get_weather`（wttr.in 免费 API）, `get_seasonal_weather` |
| 交通规划 | 3 | `set_transport_info`, `format_transport_timeline` |

最能体现"真实数据驱动"的是小红书爬虫。我集成了开源项目 Spider_XHS（7.3k 星），实现了真实的站内搜索——扫码登录后搜索"成都旅游攻略"，返回 5 条高赞笔记，最高 28003 赞。Agent 拿到这些真实笔记数据后，推荐的景点和餐厅确实更有参考价值。

### 2.3 一个关键设计：精确到分钟的时间约束

对标我手作的日本攻略，旅行规划师必须处理时间约束。比如末班车——你晚上在涩谷吃饭，22:30 吃完，末班车 23:55，交通 30 分钟，最晚几点出发？

```python
@tool
def calc_latest_departure(arrival_deadline: str, travel_minutes: int) -> str:
    """计算最晚出发时间 = 末班车时间 - 交通时间 - 10分钟余量"""
    # 23:55 - 30分钟 - 10分钟 = 23:15
    ...
```

路线规划师的 YAML 里明确要求："每天最后一段交通必须标注【最晚出发时间】和【末班车时间】"。这样生成的攻略不是泛泛的"建议晚上回酒店"，而是"23:15 前必须从涩谷出发，末班车 23:55"。

## 三、对话式修改攻略：踩坑与进化

### 3.1 Web 界面：SSE 实时推送

先说前端。用 Flask + SSE（Server-Sent Events）做了个深色主题 Web 界面：

- **表单区**：目的地、天数、人均预算、人数、偏好、出行日期、自定义交通安排
- **进度区**：4-5 个 Agent 卡片 + 实时日志流 + 进度条
- **攻略区**：Markdown 渲染 + 下载/复制按钮
- **对话区**：聊天消息气泡 + 快捷建议按钮

SSE 的好处是**服务器主动推**。Agent 每执行一步工具调用，后端通过 `on_step` 回调把事件推到消息队列，SSE 管道实时推给前端，前端更新 Agent 卡片状态和日志。用户看到的是"路线规划师正在搜索小红书 → 正在查地图 → 完成，输出 2000 字"——活生生的 Agent 工作过程。

### 3.2 对话修攻略：三次迭代

生成攻略后，用户可以对话式修改——"第2天景点太多了"、"帮我省钱"、"多加一些特色小吃"。这个功能我迭代了三次。

#### V1：让 LLM 重写整篇攻略

最初的设计很简单：把攻略全文塞进 system prompt，让 LLM 输出 `<GUIDE>修改后的完整攻略</GUIDE>`。

**问题**：攻略约 8000 字，LLM 的 max_tokens=4096 不够。修改后的攻略到第二章节就截断了，显示不全。

#### V2：章节级替换

第二次改成只让 LLM 输出被修改的章节，代码自动在原文中定位 `## 二、美食推荐` 到下一个 `---` 的内容并替换：

```python
def _replace_section(self, guide, section_title, new_content):
    """用正则匹配章节：## 标题 → 内容 → --- """
    pattern = rf'({escaped_title}[^\n]*\n)(.*?)(\n---\n)'
    ...
```

**问题**：用户一句话可能涉及多个章节——"第2天景点换成便宜的美食，重新算预算"涉及行程安排、美食推荐、预算分析三个章节。一次性输出三个章节又可能截断。

#### V3：两步模式——意图分析 + 逐章节修改（最终方案）

最终方案拆成两步：

**第一步 · 意图分析**（1 次 LLM 调用，~500 tokens）

只发攻略的章节标题列表（不发全文）+ 用户消息，让 LLM 返回 JSON：

```json
{
  "sections": ["## 一、行程安排", "## 二、美食推荐", "## 三、预算分析"],
  "reply": "好的，我来精简第2天景点，换便宜的美食，同时重新算预算",
  "details": "减少第2天景点数量，替换为平价美食，更新预算表"
}
```

输入输出都很小，几百 tokens，极快。

**第二步 · 逐章节修改**（N 次 LLM 调用，每次 ~2000 tokens）

涉及 3 个章节 → 调 3 次 LLM。每次只给一个章节的原文 + 用户意见，LLM 只输出修改后的这一个章节：

```
输入：## 一、行程安排 的原文（~2000字） + 用户的修改意见
输出：修改后的 ## 一、行程安排（~2000字）
```

代码把每个新章节用 `_replace_section()` 替换进攻略全文。

**为什么不会截断**：每次 LLM 只处理一个章节，输入约 2000 字、输出约 2000 字，4096 tokens 绰绰有余。不管涉及几个章节，分多次调用就行。

### 3.3 三个坑的修复

开发过程中踩了三个典型的坑，每一个都值得记录。

#### 坑1：Agent 步数用完后直接放弃

**现象**：预算管理 Agent 跑了 25 步后输出"Agent 在 25 步内未能完成任务"，攻略的预算分析部分完全空白。

**根因**：Agent 到达 `max_steps` 后直接返回失败消息，完全不利用已收集的信息。

**修复**：加了一个"最后一搏"机制——到达 max_steps 后，给 LLM 发一条消息："你已经用完所有工具调用步数，现在不要调工具了，直接根据已有信息整理输出完整回答"。

```python
# 到达 max_steps 后
messages.append({
    "role": "user",
    "content": "你已经使用了所有可用步数。不要再调工具，"
               "直接根据你目前已有的信息输出完整回答。"
})
response = self.llm.chat(messages, tools=None)  # tools=None 禁止工具调用
```

效果立竿见影——Agent 即使没跑完，也会把已收集的数据整理成完整输出，而不是丢一句"失败了"。

#### 坑2：预算语义不明确

**现象**：用户输入"预算 2000 元"，Agent 不确定这是人均还是总计，算出来的结果有时是 2000×1人，有时是 2000×3人。

**修复**：在三处统一口径——
- 前端标签从"预算（元）"改成"人均预算（元）"
- task 描述改成"人均预算{budget}元/人，{people}人，总预算={budget}×{people}={budget*people}元"
- budget_manager 的 YAML 增加指令"预算是人均预算，总预算=人均预算×人数"

#### 坑3：max_tokens 太小导致截断

**现象**：完整攻略约 550 行（~8000 字），LLM 默认 max_tokens=4096，重写时到一半就断了。

**修复**： 
- 全局 max_tokens 从 4096 提到 8192
- 对话修改改用两步模式，每次只处理一个章节
- `llm.chat()` 方法增加了 `max_tokens` 覆盖参数，不同场景灵活设置

## 四、技术选型与反思

### 4.1 技术栈

| 组件 | 选型 | 原因 |
|------|------|------|
| LLM | DeepSeek Chat | 便宜（百万 tokens 约 1 元）、中文好、支持 Function Calling |
| Agent 框架 | 自研 600 行 | 理解每一行代码，不被黑盒限制 |
| Web 框架 | Flask + SSE | 轻量、Python 原生、SSE 实现实时推送很简单 |
| 小红书数据 | Spider_XHS | 开源、真实站内搜索、7.3k 星验证 |
| 天气数据 | wttr.in | 免费、无需 API Key、JSON 格式 |
| 地图数据 | 高德 + Google Maps | 国内国外双覆盖（需申请 Key） |

### 4.2 几个设计决策的反思

**流水线 vs Leader 自由调度**：选流水线是对的。Leader 模式听起来灵活，但实际跑起来 LLM 会乱——可能跳过某个 Agent，或者反复调一个没用的工具。流水线保证每步必走、顺序固定，稳定性好得多。

**YAML Profile vs 硬编码**：把 Agent 的身份、指令、工具权限写在 YAML 里，而不是 Python 硬编码。好处是调 Agent 行为不需要改代码，改 YAML 就行。坏处是 YAML 的表达能力有限——复杂的条件逻辑还是得写代码。

**章节级替换 vs 整篇重写**：对话修改的三次迭代是这个项目中最大的教训。第一次想偷懒让 LLM 重写整篇，结果截断；第二次改成章节级但没考虑多章节场景；第三次拆成两步才真正解决。教训是：**涉及大文本生成的场景，要想尽办法减少每次 LLM 的输出量**。

### 4.3 成本

DeepSeek Chat 的价格是每百万 tokens 约 1 元（输入）和 2 元（输出）。一次完整的单城市规划，5 个 Agent 各跑 20-40 步，总消耗约 5-10 万 tokens，成本约 0.1-0.2 元。多城市规划约 0.2-0.4 元。对话修改每次约 0.02 元。几乎可以忽略不计。

## 六、写在最后

一天之内，从通用 Agent 框架到完整的旅行规划师，跑了通端到端流程，又在对话交互上迭代了三轮。一些收获：

1. **Agent 不神秘**。核心就是 LLM + 工具循环，60 行代码能跑通。难的是工具设计和 prompt 工程。
2. **工具是 Agent 的手**。32 个工具是这个系统能力的边界——没有小红书爬虫就找不到真实笔记，没有末班车计算就不会有时间约束。工具决定了 Agent 能做什么。
3. **减少 LLM 输出量是关键**。大文本场景下，让 LLM 整篇重写是最容易踩的坑。拆成小任务、逐个处理，才是工程上可行的方案。

项目还在继续。接下来要做多人分头行动规划——参考日本攻略里"一部分人去镰仓看海、一部分人去秋叶原朝圣"的场景。如果你对这个项目感兴趣，欢迎交流。
